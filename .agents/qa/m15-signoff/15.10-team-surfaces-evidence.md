## 1. The 404 the slice exists to fix

`members.ts` has been mailing `${APP_BASE_URL}/invite/<token>` since 15.5, to a page that did not
exist. With **no session cookie**:

```
GET /api/auth/invites/<token>  →  200 {"email":"colleague2@example.com","role":"member",
                                       "orgName":"seanrobertwright@gmail.com","expiresAt":...}
GET /invite/<token>            →  200   (NOT a redirect)
GET /team                      →  307 → /login?next=%2Fteam
```

The `/invite/` **prefix** in `lib/public-paths.ts` is what makes the first two true; `/team` proves
the gate is otherwise intact. Nav chrome on the invite page: `Logout` 0, `Monitor` 0, `Team` 0 —
GOTCHA-2 clean.

## 7. The audit log, read the only way it can be read

See `15.10-audit-trail.txt`. Ten rows, one per action, in order — and the **three 403 refusals above
wrote nothing**, which is the discriminating assertion: a refusal is not an event.

`org.renamed` has both target columns null (the object of the action is the org itself);
`member.invited` has `target_user_id` NULL with `target_email` set — the case a normalized-only
schema could not have recorded at all.

## 8. The application cannot touch it

```
$ psql "$DATABASE_URL_APP" -c "select count(*) from audit_events"
0
$ psql "$DATABASE_URL_APP" -c "delete from audit_events"
ERROR:  permission denied for table audit_events
$ psql "$DATABASE_URL" -c "select count(*) from audit_events"
8          ← unchanged
```

The zero-row read is the **absent SELECT policy**, not a failing predicate — `audit.int.test.ts`
proves it reads zero even *with* a matching org context set. The loud `permission denied` is what the
explicit `REVOKE` buys; without it the same delete would be a silent `DELETE 0`.

**Negative control, observed rather than assumed**: with the policy replaced by
`FOR ALL USING (true)` and the grant restored, tests 3 and 4 of
`packages/db/src/repositories/audit.int.test.ts` FAIL (the app role reads its rows back and deletes
them). Policy restored, suite green again.
